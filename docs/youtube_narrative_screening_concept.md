# 유튜브 내러티브 기반 종목 스크리닝 — 개념 설계 문서

> **상태**: 개념 검토(Concept Review) — 구현 전 단계
> **작성일**: 2026-05-31
> **대상 프로젝트**: 한국 주식 신호 탐지 / 알림 시스템 (기존 깃허브 프로젝트)

---

## 1. 목적

삼프로TV 등 금융 유튜브의 시장 내러티브를 정량화하여, 기존 정량 신호 탐지 시스템에 **보조 feature**로 결합한다.

핵심 가설은 다음과 같다.

> "전문가/시장 참여자가 반복 언급하는 종목·테마에는 정보가 담겨 있으며, 이를 정량 신호와 결합하면 후보 선별 품질이 개선된다."

단, 이 가설은 **검증 전까지 신뢰하지 않으며**, forward test로 예측력을 확인한 뒤에만 가중치를 부여한다(§7 참조).

---

## 2. 원안 (Initial Concept)

| 단계 | 내용 |
|------|------|
| 1 | 삼프로TV 유튜브 영상을 NotebookLM으로 오버뷰 생성 |
| 2 | 중복 언급되는 유망 종목 수집 |
| 3 | 기존 깃허브 프로젝트의 종목 분석 방법과 결합 |

골격(내러티브로 후보를 좁히고 → 정량 분석으로 검증하는 깔때기 구조)은 합리적이나, 아래 두 지점에서 구조적 문제가 있다.

- **도구 불일치**: NotebookLM은 수동 GUI 제품 → 자동화 파이프라인 부품으로 부적합
- **신호 품질**: "언급 빈도 = 유망"이라는 가정 자체의 위험

---

## 3. 원안 한계 평가

### 3.1 NotebookLM (1단계)

- NotebookLM은 영상을 직접 분석하지 않고 **유튜브 자막(transcript)에 전적으로 의존**한다. 자막 부재 시 import 자체가 실패.
- 삼프로TV는 **라이브 방송 비중이 크고, 라이브 종료 후 안정적 자막이 생성되지 않는 경우가 많아** 중요한 방송이 누락될 위험.
- 일반 사용자용 공개 API가 사실상 없음(2026년 Enterprise API는 GCP 엔터프라이즈 한정). 비공식 래퍼/크롬 확장은 ToS 회색지대 + 취약.
- 결과적으로 **"수동 GUI ↔ 자동화 코드" 사이 이음새가 매번 손작업** → 매일 돌려야 하는 스크리닝의 치명적 병목.

**결론**: NotebookLM은 "사람이 읽고 감 잡는 용도"로만 유지. 파이프라인 백본에서는 제외.

### 3.2 중복 언급 종목 수집 (2단계) — 최대 위험 지점

- **언급 빈도는 알파 신호가 아니라 관심도(popularity) 신호.** 메이저 유튜브에서 반복 언급될 즈음이면 상승이 이미 진행된 경우가 많아 → 늦은 진입 / 열기 정점 매수 위험.
  - 단기 트레이딩(종가베팅/눌림/상따) 관점에서는 **진입보다 청산·경계 타이밍 또는 테마 감지용으로 더 유용할 가능성**.
- **선택편향·이해상충**: 출연자는 이미 뜨거운 종목을 얘기하는 경향, 보유 포지션 띄우기 가능성.
- **추출 노이즈**: 한국 종목명 동음이의·약칭·계열사 혼동 심함 → ticker 매핑 + 디스앰비규에이션 필수.
- **백테스트 불가**: "특정 날짜에 무엇을 언급했는가"의 깔끔한 과거 데이터셋 부재 → 소급 검증 불가능. **forward test가 유일한 정직한 검증 경로.**

### 3.3 기존 시스템 결합 (3단계)

- 개념상 가장 타당한 부분(깔때기 구조).
- 단, **하드 필터로 쓰면 언급 안 된 종목의 좋은 정량 신호를 통째로 버리게 됨** → breadth를 내러티브 확신과 맞바꾸는 트레이드오프.
- 더 큰 문제는 **귀인(attribution) 불가**: 내러티브와 정량 신호를 하드 게이트로 섞으면 수익의 출처를 분리할 수 없어 시스템을 과학적으로 개선할 수 없게 됨.

## 4. 개선 아키텍처

NotebookLM을 파이프라인에서 제거하고, 전 과정을 코드로 묶는다.

```
[1] 수집    YouTube Data API → 삼프로TV 채널 신규 업로드 목록 (일 단위)
   │
[2] 전사    자막 있음 → youtube-transcript-api
            자막 없음(라이브) → Whisper STT
   │
[3] 추출    LLM 구조화 프롬프트 → 종목 언급 JSON
            (※ 원문 근거 문장 함께 저장 — hallucination 검증용)
   │
[4] 정규화  pykrx 종목 마스터로 ticker 매핑 + 중복 제거
   │
[5] 집계    rolling window(예: 5영업일) 언급 빈도 × 감성 → attention_score
   │
[6] 결합    기존 후보 universe에 feature로 추가 (하드 필터 ✕)
   │
[7] 검증    forward return 로깅 → 예측력 측정 후 가중치 결정
```

---

## 5. 데이터 스키마

### 5.1 언급 추출 레코드 (3단계 출력)

```json
{
  "date": "2026-05-31",
  "video_id": "abc123",
  "speaker": "출연자명 또는 unknown",
  "stock_name_raw": "원문에 등장한 종목명",
  "ticker": "005490",
  "direction": "buy | sell | neutral",
  "horizon": "short | mid | long",
  "rationale_summary": "언급 근거 1~2문장 요약",
  "source_quote": "원문 근거 문장 (검증용)"
}
```

### 5.2 집계 결과 (5단계 출력)

```json
{
  "ticker": "005490",
  "window": "2026-05-26 ~ 2026-05-30",
  "mention_count": 4,
  "sentiment_weighted": 2.5,
  "attention_score": 0.73,
  "distinct_speakers": 3
}
```

## 6. 기존 시스템 결합 방식

- `attention_score`를 **하드 필터가 아니라 하나의 feature로** `effective_confidence` 산식에 추가.
- 이렇게 하면:
  - 항목의 **한계 기여도(marginal contribution) 측정 가능**
  - **ablation**(해당 feature 제거 후 성능 비교) 가능
  - 수익 귀인 유지 → 시스템을 데이터 기반으로 개선 가능
- 결합 시점에는 가중치를 **0 또는 매우 낮게** 두고, §7 검증 결과에 따라 조정.

---

## 7. 검증 계획 (Forward Test)

소급 백테스트가 불가능하므로 forward test를 1차 검증 수단으로 한다.

1. 지금부터 **언급 데이터를 매일 로깅**.
2. 각 언급 시점 기준 **forward return 측정**: 1일 / 5일 / 20일.
3. 언급 빈도·감성과 forward return의 상관 / IC(Information Coefficient) 확인.
4. **최소 2~3개월 누적** 후 예측력 판단.
5. 예측력 확인 시에만 `attention_score` 가중치 상향. 음(陰)의 상관이면 **역지표(청산/경계 신호)로 재활용** 검토.

## 8. 리스크 / 주의사항

| 항목 | 내용 | 대응 |
|------|------|------|
| 신호 가정 오류 | "많이 언급 = 좋은 종목"이 늦은 진입 신호일 수 있음 | forward test 전 신뢰 금지 |
| 라이브 자막 부재 | 중요 방송 누락 | Whisper STT 폴백 |
| LLM 추출 환각 | 언급 안 한 종목 생성, 방향 오판 | source_quote 동반 저장·검증 |
| 종목명 모호성 | 동음이의·약칭·계열사 혼동 | pykrx 마스터 매핑 + 디스앰비규에이션 |
| YouTube ToS | 대량 전사·스크래핑 회색지대 | 개인·비상업 범위 유지, 호출 빈도 제한 |
| 귀인 손실 | 내러티브·정량 혼합으로 출처 불명 | feature 분리 + ablation |

## 9. 미결정 사항 (Open Questions)

- rolling window 길이(5영업일이 적정한가? 단기 전략에 맞춰 더 짧게?)
- 감성 가중 방식 (방향 × 발언자 신뢰도 가중 여부)
- 삼프로TV 외 추가 채널 포함 여부 (채널별 편향 관리)
- STT 비용/지연이 일일 운영에 수용 가능한지
- `attention_score`를 개별 종목 점수로 쓸지, **섹터/테마 오버레이**로 쓸지
  - 삼프로TV는 개별 종목 진입 타이밍보다 **매크로/섹터 테마 감지에 강한 채널** → 테마 오버레이 쪽이 더 적합할 가능성

---

## 10. 요약

- 원안의 골격은 합리적이나, **NotebookLM은 파이프라인에서 제외**하고 API 기반 자동화로 대체한다.
- **언급 빈도는 검증 전까지 신뢰하지 않는 실험 변수**로 다룬다.
- 기존 시스템과는 **하드 필터가 아닌 feature 결합**으로 귀인 가능성을 유지한다.
- 출력은 개별 종목보다 **테마 오버레이**로 재정의하는 방향을 우선 검토한다.
